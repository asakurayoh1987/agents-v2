# 人工监督回路 (HITL)

## 概述

人工监督回路（HITL）是一种设计模式，在关键决策点将人类判断集成到自动化系统中。在 AI 领域，HITL 出现在多种场景中——从模型训练到运行时代控制。本课程专注于 AI 智能体的**运行时审批流程**。

## HITL 在 AI 中的含义

HITL 在不同场景下有不同的表现形式：

### 1. 训练与微调（RLHF）
基于人类反馈的强化学习（RLHF）是 GPT 和 Claude 等模型进行对齐的方式。人类对模型输出进行评分，这些评分训练一个奖励模型，进而指导后续训练。这是在*训练*层面的 HITL。

### 2. 评估与质量控制
人类评估员评估模型输出的质量、准确性、安全性以及与业务目标的一致性。这发生在开发期间和部署之前。

### 3. 主动学习
当模型遇到不确定的预测时，会将这些案例路由给人类进行标注。标注后的数据反馈到训练中，迭代改进模型。

### 4. 运行时审批（本课程重点）
智能体在执行某些操作之前请求人类批准。人类可以批准、拒绝或修改该操作。这是对智能体行为的实时控制。

[译者注: RLHF 是训练层面的 HITL，而本课程关注的是运行时层面的 HITL，两者层次不同但目标相似——都是引入人类判断来提升系统表现]

## 为什么运行时审批很重要

### 信任
用户不会采用没有监督的智能体。审批让用户确信智能体不会做意外或有害的事情。随着用户看到智能体可靠地运行，信任会逐步建立。

### 责任追溯
当出现问题时，有清晰的审计线索。谁批准了这个操作？参数是什么？这对于调试、合规和法律责任都很重要。

### 审计与合规
受监管的行业（医疗、金融、法律）要求对自动化决策进行人工监督。审批创建的审计日志满足合规要求。

### 可逆性担忧
某些操作很难撤销：删除文件、发送邮件、执行 shell 命令、进行收费的 API 调用。审批为不可逆的操作提供了安全网。

### 学习与校准
审批模式可以让你了解智能体的行为。如果用户持续批准某些操作，后续可能自动批准。如果持续拒绝，可能需要调整智能体的方法。

## 审批流程架构

### 1. 同步审批（我们的实现）
智能体循环在等待人类输入时暂停。智能体进程保持运行，循环只是在审批 promise 上阻塞。

**优点：**
- 实现简单
- 智能体保留完整上下文
- 不需要持久化层

**缺点：**
- 无法扩展到多用户
- 无法在 HTTP 请求/响应中工作（超时问题）
- 用户必须在需要审批时在场

**适用于：** CLI 工具、本地开发、实时交互式会话

[译者注: 同步审批的核心是 `await` 操作，代码会阻塞直到用户做出决定。这种方式简单直观，但限制了使用场景]

### 2. 异步/后台智能体
智能体完全停止执行并持久化其状态。审批请求被发送到某个通知系统。当人类响应时（几分钟后、几小时后或几天后），智能体从持久化状态恢复。

**优点：**
- 跨越时间边界工作
- 支持多个并发的智能体会话
- 适用于无服务器/HTTP 环境

**缺点：**
- 需要状态持久化（数据库、文件存储）
- 需要恢复/水合逻辑
- 基础设施更复杂
- 恢复时智能体上下文可能过时

**适用于：** 生产部署、多用户系统、长时间运行的工作流

### 3. 混合方法
某些系统对快速决策使用同步审批，但对较长的等待回退到异步。或者对某些操作自动批准，而对其他操作需要异步审批。

## 审批粒度

有很多方法来决定什么需要审批：

### 按工具审批
- 批准每次对 `shell_command` 的调用
- 自动批准 `read_file`，但 `write_file` 需要审批

### 基于输入的审批
- 如果 `shell_command` 是 `ls` 或 `cat`，自动批准
- 如果 `shell_command` 包含 `rm` 或 `sudo`，需要审批
- 只有当路径在特定目录时才批准 `write_file`

### 基于会话的自动批准
- "在本次会话的剩余时间内信任此工具"
- "信任所有符合此模式的工具"
- 随着信任的建立，用户授予递增的权限

### 基于风险的评分
- 根据工具 + 输入 + 上下文计算风险分数
- 低风险：自动批准
- 中风险：需要审批
- 高风险：完全阻止，需要显式覆盖

### 基于时间/成本
- 如果操作耗时 < 5 秒，自动批准
- 如果 API 成本 < $0.01，自动批准
- 对昂贵或长时间运行的操作需要审批

[译者注: 审批粒度的设计需要在安全性和用户体验之间取得平衡。过于细粒度会导致审批疲劳，过于粗粒度则可能带来安全风险]

## 通知渠道

对于异步审批，请求需要以某种方式传达给人类：

- **应用内通知** - 用户在仪表板中看到审批队列
- **邮件** - 批量或实时通知
- **Slack/Teams** - 带有批准/拒绝按钮的交互式消息
- **短信** - 用于紧急、高优先级的审批
- **电话** - 用于关键、时效性强的决策
- **移动推送** - 原生应用通知

## 未来愿景：智能体收件箱

想象一个未来，你有多个智能体在后台运行：
- 监控邮件并起草回复的智能体
- 跟踪日历并建议优化的智能体
- 监控代码库问题的智能体
- 处理客户支持分诊的智能体

每个智能体偶尔会有问题或需要审批。你的"智能体收件箱"会聚合所有这些：
- 按紧急程度和重要性优先排序
- 尽可能批量处理（"批准所有 5 次文件写入？"）
- 基于过去决策的智能默认值
- 可委托给其他人甚至其他智能体

这是自然的演进：从批准每个操作，到批准类别，再到管理半自主智能体的组合。

[译者注: 智能体收件箱的概念类似于现代操作系统中的通知中心，是将多个智能体的协作请求统一管理的界面模式]

## 代码

### src/agent/run.ts

在执行每个工具调用之前添加审批逻辑。关键洞察是我们**顺序**处理工具调用，这样如果任何审批被拒绝，我们可以停止：

```typescript
// Process tool calls sequentially with approval for each
let rejected = false;
for (const tc of toolCalls) {
  const approved = await callbacks.onToolApproval(tc.toolName, tc.args);

  if (!approved) {
    rejected = true;
    break;
  }

  const result = await executeTool(tc.toolName, tc.args);
  callbacks.onToolCallEnd(tc.toolName, result);

  messages.push({
    role: "tool",
    content: [
      {
        type: "tool-result",
        toolCallId: tc.toolCallId,
        toolName: tc.toolName,
        output: { type: "text", value: result },
      },
    ],
  });
  reportTokenUsage();
}

if (rejected) {
  break;
}
```

`await callbacks.onToolApproval(...)` 返回一个 Promise，当用户做出决定时解析。这就是同步阻塞发生的地方——智能体循环在这里等待，直到 promise 解析。

[译者注: 这段代码展示了同步审批的核心实现。关键点在于使用 `for` 循环顺序处理（而非 Promise.all），这样一旦某个操作被拒绝，后续操作就不会执行]
